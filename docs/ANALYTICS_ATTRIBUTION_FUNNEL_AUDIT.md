# 匿名归因、转化漏斗与首次激活：完成性审计

审计日期：2026-08-17
审计对象：`agent/visitor-attribution-funnel-analytics` 合并到 `preview` 的集成版本
对照文档：[ANALYTICS_ATTRIBUTION_FUNNEL_PLAN.md](./ANALYTICS_ATTRIBUTION_FUNNEL_PLAN.md)

## 一、结论

这轮实现已经覆盖了计划的主要产品骨架，可以进入 `preview` 供真实用户试用，但还不能称为“完整闭环”。当前完成度建议标记为：

> **核心采集链路：已完成；首次激活漏斗：基本完成；跨设备归因、后台首触归因和运行时质量验证：部分完成。**

本轮已保留并合入以下能力：

- 持久化匿名 `visitor_id`、会话 `session_id` 和首次来源信息。
- `/r2` 短链归因、UTM、首个 referrer 和 SPA 页面事件。
- `signup_started`、`signup_confirmed`、`intake_started`、`natural_language_parsed`、`first_plan_applied`、`first_task_completed`、`review_completed`、`schedule_repair_applied` 八个核心事件。
- 本地 outbox、离线重试、事件白名单、服务端字段清洗和 `visit_logs` 索引。
- 邮箱未验证提示和重新发送验证邮件入口。
- 可恢复的交互式教程及教程数据空间隔离；教程行为不会再写入真实漏斗事件。

## 三、必须关注的缺口

### P0：账号确认不能只依赖注册浏览器

当前 `signup_confirmed` 需要本地保存的待确认注册信息与当前浏览器中的 session 对上。用户可能在手机注册、电脑点击邮件，或者清理了浏览器缓存；这时邮箱确实完成了确认，但事件不会归因到注册漏斗。

建议下一步增加服务端确认来源，优先顺序如下：

1. 使用 Supabase Auth webhook / Edge Function，在用户 `email_confirmed_at` 首次出现时写入服务端事件。
2. 服务端事件以 `user_id` 为账号漏斗主键，以最近一次有效的 `visitor_id` 或注册归因快照作为辅助归因。
3. 客户端事件继续保留，但服务端对同一用户和事件类型做幂等去重。

### P1：来源映射应从前端硬编码迁移到统一映射表

当前 `/r2` 的映射虽然可以工作，但写在 `src/lib/analytics.ts` 中。新增活动需要重新发版，且不能保证短链接重写、首触快照和后台报表始终使用同一套配置。

建议建立一份单一真相：

```text
短路径 -> source -> campaign -> content -> 开始时间 -> 结束时间
```

前端只记录 `landingPath`，服务端在入库时完成映射；本地仍可保留映射作为无网络时的降级显示。

### P1：漏斗事件应在动作边界发出

现在 `AnalyticsObserver` 通过 AppState 前后快照判断“首次排期”“首次完成”“复盘”和“修复”。这种方式能快速接入，但有几个边界：

- 页面首次加载时已有计划，不会补发或校正历史激活状态。
- 同一浏览器的教程、游客空间、个人空间必须严格隔离，否则会污染真实漏斗；本轮已加入教程空间跳过逻辑，但账号空间切换仍应在服务端按用户重算。
- 一个动作可能产生多个状态变化，事件元数据不一定能准确说明用户点击的入口和最终结果。
- 自然语言解析依赖按钮文字和 `.intake-import-preview` DOM，文案或组件结构变化会让事件失效。

后续应在 `prepareIntakeBatch`、正式应用排期方案、完成任务、保存复盘和确认修复方案等领域函数中直接发出事件，UI 观察器只作为兼容兜底。

### P1：管理端查询要区分“匿名访问漏斗”和“账号激活漏斗”

匿名留存应按 `visitor_id` 计算；注册后激活、首个计划和邮箱确认应优先按 `user_id` 计算。一个 visitor 可能有多个账号，也可能在多个设备上使用同一账号，不能用同一字段覆盖所有指标。

报表应保存首次触点快照，而不是对整个时间段做 `max(utm_source)`。建议数据层保留：

- `first_touch_source`
- `first_touch_campaign`
- `first_touch_path`
- `signup_user_id`
- `signup_at`
- `email_confirmed_at`
- `first_plan_at`
- `first_task_completed_at`

## 四、邮件验证体验审计

代码已经补上了“检查邮箱”和“重新发送验证邮件”的入口，但还需要通过真实邮箱抽样验证：

- QQ、163、Outlook、Gmail 是否进入垃圾箱或被延迟。
- 注册成功后的提示是否明确说明“必须点击邮件完成验证”。
- 重发是否有冷却时间，避免重复点击和邮件轰炸。
- 邮件确认后回到产品，是否能在不重新注册的情况下完成登录并继续首次建档。
- 失败时是否给出可执行的帮助，而不是只显示原始 Supabase 错误。

建议补充事件：`signup_created`、`email_verification_sent`、`email_verification_resent`、`email_verified`、`signup_failed`、`verification_help_opened`。其中确认成功仍以服务端 auth 状态为准。

## 五、当前验证结果与可信度

已执行或继承的检查：

- `scripts/visit-log-v0815.mjs`：静态采集链路检查通过（26/26）。
- `scripts/tutorial-flow-audit.mjs`：教程流程静态检查通过（63/63）。
- 集成分支使用单 worker `forks` 运行 Vitest：6 个测试文件、27 个测试通过。

这些结果只能证明关键字符串、文件和部分行为存在，不能证明真实浏览器中的：

- localStorage 禁用、隐私模式和跨标签页行为；
- 离线入队、恢复联网后的顺序和重复提交；
- API 限制、无 token、错误 JSON 和服务端去重；
- 同浏览器多账号、跨设备邮箱确认；
- 页面文案或懒加载变化后 `app_page_view` 是否仍然触发。

因此本轮合并前会以生产构建、现有测试和脚本审计作为门槛；运行时分析测试应列入下一轮质量门禁。

## 六、建议的后续顺序

### 下一轮 P0

1. Auth webhook / Edge Function 写入 `email_verified` 和 `signup_confirmed`。
2. 为 `analytics_events` 或 `visit_logs` 增加服务端幂等键和唯一索引。
3. 将首次激活与账号 `user_id` 绑定，游客和教程事件只作为匿名行为，不进入账号激活漏斗。
4. 把短链映射和首次触点快照固定为服务端可查询结构。

### 下一轮 P1

1. 领域动作直接埋点，保留 `AnalyticsObserver` 作为兜底。
2. 将页面事件改成应用路由/页面状态直接发送，删除对标题文本的依赖。
3. 增加邮箱重发冷却、验证帮助和失败事件。
4. 为分析模块补 Vitest：来源优先级、首次保存、事件去重、outbox 重试、隐私字段清洗。

### 下一轮 P2

1. 管理端提供访问、注册、验证、首次计划、首次完成、复盘和修复的漏斗看板。
2. 增加 D1/D3/D7 留存，并同时展示 visitor 留存和账号留存。
3. 对小红书不同内容使用 `r1/r2/r3` 或更长的短路径映射，不在链接中暴露复杂 UTM。
4. 当数据不足或跨设备无法恢复时，在看板中显示“估算/缺失”，不伪造精确转化率。

## 七、最终判定

本分支适合合入 `preview`，因为计划中最关键的采集骨架、教程和本地可靠性已经存在；但 PR 描述必须明确“跨设备邮箱确认、后台首触映射、运行时质量门禁尚未完全交付”。这三项不能用静态审计通过来替代，后续应作为正式的 P0/P1 任务继续跟踪。
